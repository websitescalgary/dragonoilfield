# Dragon V4 — Rebel staging and launch checklist

Status: locally tested, not deployed and not approved for go-live. Original-photo transfer, Rebel runtime checks, authenticated mail configuration, and Billy's real inbox confirmation remain pending.

## Prepare staging

1. In Rebel's hosting control panel, create a new, separate WordPress installation on a staging or temporary HTTPS hostname. Do not replace the existing website. Back up existing website files, database, and current DNS records first; confirm the backup can be restored. Exact control-panel labels depend on the Rebel hosting plan.
2. Use the current stable WordPress release and a currently supported PHP version supported by Rebel and WordPress. Local compatibility was tested on WordPress 6.4.3 / PHP 8.2.17; that old QA runtime is not a production version recommendation. Confirm mysqli, GD or Imagick, mbstring and fileinfo; writable uploads; outbound HTTPS; at least 256 MB PHP memory; upload_max_filesize at least 16 MB; post_max_size at least 20 MB. Record actual values in Tools → Site Health → Info → Server and Media Handling. Verify HTTPS without certificate warnings. Disable search indexing in Settings → Reading during staging and use hosting access protection if available.
3. Appearance → Themes → Add New Theme → Upload Theme: select dragon-oilfield-theme-v4-final.zip, Install Now, Activate. The displayed theme name is Dragon Oilfield Supply, version 1.1.1.
4. Plugins → Add New Plugin → Upload Plugin: install and activate dragon-lead-form-v4-final.zip (1.2.1) and dragon-site-setup-v4-final.zip (1.0.1). Deactivate earlier Dragon V2/V3 components. Do not upload the local QA hooks, database, scripts, or test fixtures.

## Import originals and edit Home

5. While the original host is still accessible, open Tools → Dragon Site Setup. Click “Import original photos and set up editable Home page.” The supplied pattern references 11 unique originals. The tool uses WordPress sideloading APIs, keeps successful partial imports, refuses homepage creation until all 11 are local, and reuses valid files on retry. If a host firewall or timeout blocks an image, allow the approved source host in Rebel's outbound settings or ask Rebel support; retry. Do not switch DNS to work around download failures.
6. Confirm the success message; Media → Library must show the imported originals. Open several attachment details and check that the file URL is the NEW staging site's uploads path and the file loads. Inspect all 11. The full downloadable originals have not yet been verified in this cloud task. Inline supplied equipment images are approved references, but their downloadable binary files were not made available to the local runner. Do not substitute QA logo fixtures or Shopify screenshots. The oil-drop image is not used as equipment photography.
7. Pages → Home → Edit opens native Gutenberg content: 178 blocks, including image/cover blocks, headings, paragraphs, columns, lists, buttons and complete section groups. Use List View to select a section; select an image and click Replace → Media Library to replace it. Edit product category texts directly. No Elementor, locked HTML widgets, or editing PHP is required. Header/footer branding is edited in Appearance → Editor. The front-page template renders Home's saved post content.
8. Save a small test edit and rerun Tools → Dragon Site Setup. Verify that Home is preserved. Existing Home content is deliberately never overwritten; adding new photos later should be done in Media → Add New and Pages → Home → Edit.
9. View the page while logged out. Browser developer tools → Network → Img: equipment photos must come from the NEW site's uploads path, with successful responses, no requests to the old photo host. Verify there are no mixed-content requests. Fonts are bundled in the theme. Check 1440, 1024, 768, 390 and 320 px with the real photos loaded, keyboard focus, mobile menu, every CTA's section target, footer credit, text wrapping and field labels. Category cards are intentionally non-clickable. Obtain owner review of content, photography, specifications and layout. Performance with original photos remains pending; optimize copies through WordPress as needed while retaining originals.

## Configure and prove mail delivery

10. Settings → Dragon Contact Form: confirm billy@dragonoilfield.com and Save Settings. Install an appropriate supported SMTP/API plugin through Plugins → Add New, or use Rebel's supported authenticated mail transport. Obtain actual server/port/encryption/sender settings from Rebel or the chosen provider; do not guess them. Enter credentials securely in hosting/plugin settings, never source files or chat. Configure a verified sender on the authorized sending domain, enforce that From address, and use authentication with TLS verification enabled. The form sets the visitor's valid email as Reply-To; it does not spoof the visitor as From.
11. Keep all existing MX, SPF, DKIM and DMARC records intact. If sender verification needs DNS changes, inventory existing records and obtain explicit approval for the precise additive/merged changes first. Never create a second SPF record or replace mail routing as part of website deployment.
12. Send a real provider/plugin test and a clearly labeled form enquiry, then have Billy confirm actual inbox receipt (check spam and authentication headers). A wp_mail_accepted record means only that WordPress accepted the send, not that it reached the inbox. Do not mark delivery passed until Billy confirms receipt.
13. On staging submit Name + phone only; Name + email only; Name + both; no contact; malformed phone with valid email; malformed email with valid phone; blank Name/Enquiry. Space legitimate tests at least 45 seconds apart because of the per-IP limiter. Valid tests must save private Dragon Inquiries; supplied phone and email must both be present when given. Invalid tests must save nothing. Check Settings recipient, Dragon Inquiries → individual enquiry, and admin custom-field metadata dragon_email_attempt if needed. wp_mail_failed enquiries remain stored for follow-up. Honeypot and nonce/rate-limit tests passed locally; verify hosting caching/security plugins do not cache expired form nonces or block admin-post.php. Exclude the form page from long-lived full-page caching unless nonce refresh is implemented.
14. Verify only authorized administrators can read stored enquiries. Enquiries contain personal information: define retention and deletion practices before launch. Local mail interception fixtures are never production configuration.

## Go-live gate — requires explicit permission

15. Record owner approval of staging, all original images, mail receipt and backup/rollback. Only then request explicit go-live permission. Deployment permission does not imply permission to change DNS or email records.
16. With separate DNS approval, plan exact GoDaddy web-host A/AAAA/CNAME changes supplied by Rebel, hostname redirects, TLS issuance, and TTL. Preserve MX/TXT mail records and verify SPF/DKIM/DMARC remain correct. Keep original hosting and backups available for rollback. Import originals before any cutover.
17. After authorized cutover, update WordPress URLs using a serialization-aware migration tool, verify HTTPS and canonical www/non-www redirects, Settings → Permalinks → Save Changes, and recheck local media, page editing, navigation, saved enquiries, SMTP delivery and actual inbox receipt. Remove staging indexing restrictions only on the public production site. Keep staging protected.
